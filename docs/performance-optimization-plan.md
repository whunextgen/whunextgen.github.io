# 性能优化计划

## 已完成

1. 前端相同会话内并发 GET 去重，降低 React 挂载/重复 effect 造成的重复请求。

## 下一步（收益高、风险低）

1. 增加 request id、API 名称、总耗时、飞书请求次数、分页数、缓存命中/未命中和响应条数日志；禁止记录 token、密码和财务明细。
2. 用有效测试账号建立真实业务基线，覆盖登录、Dashboard、Workspace、API Resources、项目/预算/支出页面。
3. 检查 Finance 页面初始化，复用已完成的请求，不重复调用相同接口。
4. 为资源中台提供面向页面的轻量聚合接口，明确字段边界，避免“超级接口”。
5. 将只读配置和模型目录与用户私有数据分离，设计短 TTL/长 TTL 和写后失效策略。

## 中期

1. 将 `financeWorkspace` 拆为按页面和实体类型的查询接口。
2. 优先利用飞书过滤条件，减少整表读取；评估按实体类型、项目和时间范围分页。
3. 审查 `saveFinanceEntity` 的精确定位路径，确认可按业务键查询后再移除写前整表扫描。
4. 对登录、Finance、Leader、Excel 解析和资产/API 管理做路由级拆包。

## 禁止事项

- 不改变飞书事实源。
- 不把权限、个人申请、审批、资产明细或支出明细放入公共 CDN 缓存。
- 不用内存 Map 伪装成可靠持久读模型。
- 未有一致性、重试和补偿方案前，不切换 Supabase 为主数据源。
